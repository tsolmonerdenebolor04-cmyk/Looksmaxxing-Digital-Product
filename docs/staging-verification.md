## Opt-in real Supabase suite

Ask the operator before secret use and before hosted fixture writes. Do not retrieve secret keys through GitHub, browser code, logs or chat. Copy .env.staging.example to ignored .env.staging and configure the staging secret and publishable keys locally. The template URL and explicit RUN_STAGING_INTEGRATION value must remain exact. Generic SUPABASE_* variables are never used as a fallback.

After permission, run:

    npm run test:staging

This runner uses real Supabase REST insert/select/update/delete calls and the real store/authentication/recovery/report handlers. It does not start Vercel or use Gemini or QPay. It creates synthetic noncustomer fixtures and checks:

1. Zero-row schema/read preflight, report insert/select and preview-only creation.
2. Cookie-authenticated unpaid recovery and denial of full access.
3. Missing/forged cookie denial.
4. Publishable-key direct reads and status tampering blocked by grants/RLS.
5. Checkout remains unavailable.
6. A **synthetic** paid fixture authorizes owner access; paid report status alone is insufficient.
7. A refunded fixture revokes access; expiry blocks preview and full retrieval.
8. Cleanup of only the report IDs generated by that run, with dependent fixture events/payments first.

The paid fixture is labeled synthetic in provider_invoice_id and raw_provider_response. It tests access control and is never claimed as a real verified QPay settlement. The runner creates no invoice, callback or merchant confirmation. It does not alter schema, RLS, hosted environment settings or unrelated data.

Cleanup runs in finally. If connectivity/permissions prevent cleanup, the run fails and prints only the affected report IDs for manual cleanup; the operator must remove only that run's fixture IDs, never truncate tables. The service-role/secret key must have the expected staging-only privileges. Do not use production credentials.
